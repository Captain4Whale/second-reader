# Q1 Rubric 设计说明

这份文件记录 rubric 为什么这样定。判定时用 `q1-v3.4.md`（标准）和 `q1-annotation-guide.md`（人工标注顺序），不需要读这里。

## 这份 rubric 的定位
- rubric 给 judge 用，人类 judge 和 LLM judge 都是。它只定标准：什么样算过、什么样不过、每一项问的是什么。
- 一个判定项的标准如果主观，rubric 里要配一个检验方法（如"用大白话复述""能不能换成一句具体的话"）。这些方法是在定义标准，属于 rubric。
- 给 judge 哪些材料、一个 judge 判几项、要不要把复述写成输出，属于 judge 设计，不写进 rubric。
- rubric 写"观察者知道什么"（读过锚点之前、没读过之后），不写"judge 能看到什么"。前者是标准的一部分；后者取决于判哪一项，比如判剧透的 judge 必须看后文，但观察者本人不知道后文。

## 关键设计选择
- **"过"的定义是"比没看到要好"，不是"没有毛病"**。所以分价值、伤害、摩擦三层，摩擦只作标签。
- **产品取向是产品选择，不是普遍标准**。换一个产品，比如给研究者用的学术注释本，标准会不一样。
- **N1 看内容，"读着费劲"看表达**。N1 只看读懂之后得到的内容，"读着费劲"只看读懂花了多少力气，同一个问题不在两处扣。这样以后拆 judge 时两项互相独立，统计时也分得开。"有东西没送到"只管内容缺了一块，"太简练"是关键一步写了但点到为止，二者用"能不能指出哪一句写了关键那一步"来分。
- **"交代来路"只在批注的价值落在一个有名字的说法上时要求**。一般背景事实不需要。
- **文档结构：流程、定义参考、例子分开**。Note 和 Highlight 各自先给判定步骤（每一步只写问什么、怎么检验、怎么算），再给定义参考和按步骤分组的例子。所有列表都写明是"任一满足"还是"同时满足"。目标是新人照着判定步骤就能走完一条批注。
- **"读着费劲"放在第一步，检验是"读一遍后复述"加"能否改写"**。"费不费劲"本身是感受，不好判；"读一遍后说不说得出它讲了什么"是一个能做、事后也能核对的动作。它必须排在最前面，读过几遍之后就判不了第一遍读不读得懂了。"能否改写得更直白又不丢东西"用来排除想法本身就绕的情况。
- **"读着费劲"留在伤害层，不降为摩擦**。共读场景里读者不会停下来拆旁注的句子，看着绕就跳过，批注的价值实际送不到；跳过几次之后，读者会连好批注也一起跳过。而且"有知识但说得太隐晦"是目前最该优先修的问题，放在标签里不影响通过率，用 judge 迭代 prompt 时就推不动它。N1 和否决项分开记录，"N1 过、只因读着费劲而不过"的条数随时可以算出来，放在哪一层不丢信息。
- **"下文马上讲了"写进 N1 自己的判不过条件**。不写进去，N1 可能因为内容对观察者是新的就判过。

- **每一项写成可以单独判的形式**。以后的 LLM judge 是一项一个，所以 rubric 不能依赖判定顺序。Note 和 Highlight 各自先给总览表（有哪些项、属于价值/否决/标签哪一类、各问什么、怎么合成结论），再逐项展开，每项写问题、判过与不过（写明"任一"或"同时"）、检验、这一项不管什么、例子。"不管什么"取代了原来靠顺序保证的分工，例如 N1 不管表达，读着费劲不管内容；"下文马上讲了"和"有剧透"用同一句"紧接着几段"划界，两个 judge 才不会对同一条批注给出矛盾的结论。参考：Hamel Husain 和 Shreya Shankar 的"一个 judge 只管一个失败类型、二元输出"，Langfuse 反对"上帝 judge"，以及"写清楚一项不管什么和写定义一样重要"的做法。
- **判定顺序挪到人工标注说明**。人工一次判完所有项时，顺序仍然重要："读着费劲"要在第一遍读完时判。这份顺序放在 `q1-annotation-guide.md`，不放在 rubric 里。LLM 的读着费劲 judge 每次都是第一次读，天然满足这个条件。
- **N1 的失败类型只供人工诊断**。LLM judge 用多选分类输出时，很难判断该选几个，所以 N1 judge 只判过或不过。哪一类失败多到值得单独盯，再给它做一个独立的二元 judge。

- **N1 给"其他写法"留口子**。三种写法是从两本书、几十条批注里归纳的，盖不全是正常的；只认见过的好批注，就看不到更好的。口子的门槛取三种写法共同的东西（有原文没有的新东西、具体、交代来路），所以不比三种写法低；"像哪种就按哪种判"防止它被当成后门；"必须写一句"让以后能归类、升级成新写法。和不过一侧的"rubric 未覆盖"对称。

- **二元判定加标签**的结构，参考了 Hamel 的 evals 方法和翻译行业的 MQM。

## 标签值不值得保留
看两点：这个摩擦读者真的感觉得到吗？它出现得多了，会不会去改 prompt？两个都是才留。

待定：有空话和冗余要不要合并、老师口吻要不要去掉。等新批次的数据出来再定。

## 待验证
- **"读着费劲"能不能当一票否决**：这一项注定比 N1 主观。新批次标完看它的"拿不准"多不多；做 judge 时看 LLM 和人的一致率。一致率低，就降为标签。

- **哪些项能做成 LLM judge**：一个 judge 大约需要 20 条过、20 条不过的人工标注。"有错误信息"目前没有真实样本，"有剧透"也很少，短期内做不了 judge，先靠人工抽查或别的办法。

- **"其他写法"会不会被钻空子**：用 judge 迭代 Digest prompt 时，生成的批注可能越来越多地落进 judge 最宽松的"其他写法"，通过率涨了质量却没涨。每轮全部人工回看，并盯住占比。

## 例子的使用限制
rubric 里的例子都来自开发集（DIAG-001）。这些条目：
- 不能用来测 judge，测试时要排除
- 不能放进生成用的 prompt 当范例
